# PiCoCo — CLAUDE.md

Raspberry Pi Pico 2 to Tandy Color Computer (CoCo 1/2/3) cartridge interface. The
MVP makes the CoCo boot a DriveWire-enabled HDB-DOS ROM over `/CTS` and exposes a
Becker-port peripheral at `$FF41`/`$FF42` under `/SCS` so the Pico can serve as a
real DriveWire device.

## Before touching anything, read these

In order:

1. `docs/hardware-design.md` — block diagram, signal table, BOM, PCB rules.
2. `docs/firmware-architecture.md` — PIO state machines, DriveWire integration, bring-up plan.
3. `docs/kicad-workflow.md` — how to drive KiCad against this repo.

The plan-mode doc that birthed the redesign is at
`~/.claude/plans/check-this-project-cuddly-iverson.md`.

## Regenerating artifacts

- Schematic: `python3 tools/gen_schematic.py` — rewrites `PiCoCo.kicad_sch` from the
  declarative `pin_nets` dicts inside. After regen, in KiCad:
  1. Close & reopen the schematic so KiCad drops its cache.
  2. Run **Tools → Update PCB from Schematic** and tick "Delete footprints with no
     corresponding symbol" so v1 orphans disappear cleanly.
- PCB placement: `python3 tools/place_pcb.py` — edits the first `(at X Y rot)` of
  each footprint. Backs up via `PiCoCo.kicad_pcb.pre-place`. Idempotent; re-run after
  editing the `PLACEMENT` dict. Will NOT preserve routing or zones if the user
  has started routing. **The main board is now fully routed** (`PiCoCo/PiCoCo.kicad_pcb`
  is hand-finished and authoritative) — re-running `place_pcb.py` on it destroys that
  routing; don't run it again unless you intend a full reroute.

## Hard rules

- **Never hand-edit `PiCoCo/PiCoCo.kicad_sch`.** Modify `tools/gen_schematic.py`
  (declaratively; search for a `pin_nets` block) and regenerate.
- **Never use TXB0108 / TXS0108E / 74FST3257 for this bus.** The project was
  redesigned specifically to get rid of them — weak auto-sensing drivers, mux
  confusion. Use `SN74LVC245A` at 3.3 V for all four buffers; U10's A side
  (pins 2..9) is the Pico, B side (18..11) is the cart. See
  `docs/hardware-design.md` §4 for why.
- **Never connect peripheral logic to the Pico's `3V3_OUT` pin.** VSYS is fed
  from +5V via D2 Schottky (`VSYS_PICO` net). 3V3_OUT stays NC.
- **Pin assignments are PIO-optimized** — see hardware-design §3.2. Don't move
  GPIO assignments without updating `docs/firmware-architecture.md` at the same
  time. `bus_watcher` assumes A0–A13 contiguous on GP8–GP21 + /R/W on GP22 so
  one `IN PINS, 15` captures the whole address in a single PIO cycle. Firmware
  uses **`OE_BUS` on GP26** and **A13** to distinguish ROM ($C000–$FEFF, the
  full `/CTS` window) from Becker ($FF40–$FF5F) cycles — do NOT route /CTS or
  /SCS to the Pico as separate signals.
- **GP27 is the /HALT drive (`HALT_GATE`).** Firmware drives GP27 HIGH to hold
  /HALT low (Q2 N-FET on), LOW to release. Defaults to held at boot via R7
  (10 kΩ, v2.3.1 — was 100 kΩ, which the RP2350's own reset pull-down beat)
  pull-up on the gate. Do not repurpose this pin without also changing the
  /HALT circuit.
- **U15 is a 74LVC00 (SOIC-14) wired NAND-NAND**: `SEL_N =
  NAND(CTS_BUF,SCS_BUF)`, `OE_BUS_RAW = NAND(SEL_N,E_BUF)`; gates 3/4 are
  grounded (unused). `OE_BUS_RAW` goes through R11 33R to `OE_BUS`, low only
  while a cart address is selected and E is high. The E qualification closes
  a write-cycle contention window. Firmware controls only bus direction via
  its own GPIO pindirs; if you move /OE logic back into firmware you'll
  consume a GPIO that's not budgeted (JP2 exists for exactly that swap, see
  below).
- **Net-name convention**: buffered signals at U10/U11/U12/U13 outputs end in
  `_BUF` (e.g., `RW_BUF`, `CTS_BUF`, `SCS_BUF`, `RESET_BUF` — every buffered
  net, including reset, gets the suffix). `_RAW` variants are the
  pre-termination side of series resistors R11/R12. `_B` and `_DBG` as
  suffixes are NOT used anywhere — earlier drafts had `CTS_B`/`SCS_B`/`RW_B`/
  `RESET_DBG` as orphan or misleading nets. If you see those names in future
  edits, that's a fab-blocking bug; `gen_schematic.py`'s `check()` asserts
  against both.
- **JP2 default 1-2 (hardware /OE)**: bridges `OE_BUS` (U15 output) to U10's
  `/OE`. Cutting 1-2 and bridging 2-3 lets firmware drive U10 `/OE` from a
  Plus-W pad-grid GPIO instead. R25 10 kΩ pulls `U10_OE` up to +3V3 so an
  unprogrammed module in that 2-3 position can't float the CoCo bus enabled.
  **JP3 default 1-2 (audio on header pin 34, v2.3.1)**: bridges `AUDIO_PWM`
  to the module's header pin 34 (GP28 on a Pico 2, GP42 on a Plus-W), so a
  Pico 2 build has sound out of the box. Cutting 1-2 and bridging 2-3 puts
  `E_BUF` on that pin instead (needed only by the v2 PIO engine, a
  Plus-W-only path — a Plus-W gets audio from its own pad-grid GP34 and
  leaves JP3 at default). **JP4 (v2.3.1, open by default)**: a 2-pad solder
  jumper tying `Q_CART` to `CART_CART` — the classic Program Pak autostart
  trick, for a Pico 2 build with no spare GPIO to drive `/CART`. Bridging JP4
  breaks HDB-DOS and any DK-signature DOS ROM (it pulses `/CART` forever, so
  the CPU jumps to $C000 as code on every cycle). **JP5 (v2.3.1, open by
  default)**: a 3-pad solder jumper sharing header pin 34 with JP3 — pad 1
  `CART_DRV`, pad 2 `PICO_P34`, pad 3 `NMI_DRV`. Never bridge both JP3 and
  JP5. 1-2 on a Pico 2 gives a firmware-pulsed `/CART` via the now-populated
  Q4/R16/R18 stage; 2-3 gives a firmware-pulsed `/NMI` via the DNP Q3/R15/R17
  stage instead (fit all three to use it). **C16 (v2.3.1)**: 10 µF local
  +3V3 bulk at the buffer row, next to U11/U12. **J1 "EXP (Plus-W)"
  (v2.3.1, DNP)**: a 1x5 header breaking out the four previously
  no-connect Plus-W pad-grid pins (`EXP_GP35/43/44/45` + GND) — meaningless
  on a Pico 2, where GP35 instead carries the module's own SWDIO pad.
  `gen_schematic.py` also writes `Pico-Carrier` and `74LVC00` into the local
  library (`libraries/PiCoCo.kicad_sym`, `libraries/
  PiCoCo.pretty/Pico-Carrier.kicad_mod`) as a side effect of regenerating
  the schematic; never hand-edit those two.

## Known quirks

- **ERC always reports 1 error**: `pin_to_pin` between `P1 Pin 33 GND@1` and
  `P1 Pin 34 GND@2` (both declared `power_output` by the `PiCoCo:COCO-CART`
  symbol). Library quirk, pre-existing, ignore.
- **`kicad-cli pcb drc` crashes with a Swift runtime error only inside the
  Claude Code sandbox.** Run it with the sandbox disabled and it works,
  including `--schematic-parity` (verified KiCad 10.0.6, 2026-09-05). ERC,
  render and Gerber export work sandboxed. `tools/gen_fab.sh` still skips
  DRC; run it separately before ordering. It also silently falls back to
  KiCad's default design rules unless `PiCoCo.kicad_pro` sits beside the
  board file being checked — copy the `.kicad_pro` next to any scratch
  copy of the board before running DRC on it.
- **`tools/gen_breakout.py` must run under KiCad's bundled Python**
  (`/Applications/KiCad/KiCad.app/Contents/Frameworks/Python.framework/Versions/Current/bin/python3`)
  because it drives the pcbnew API. It writes `breakout/` (both boards),
  `libraries/PiCoCo.pretty/COCO-CART-FINGERS.kicad_mod`, and the
  `COCO-CART-FINGERS` symbol inside `libraries/PiCoCo.kicad_sym`.
- **Never pair the breakout with a Raspberry Pi cobbler.** They bus GND
  and 5V pins on the adapter; use `breakout/PiCoCo-Cobbler` (1:1).
- **`COCO-CART-2.1X1.75` fingers end 1.30 mm from the edge** (trimmed by the
  shared `FINGER_TRIM` regex in `gen_schematic.py`, also used by
  `gen_breakout.py` for `COCO-CART-FINGERS`) so JLCPCB's 1.13 mm 30° bevel on
  1.6 mm stock doesn't cut into them. Already done on both boards; keep the
  trim if you regenerate.
- **No 2×20 debug headers and no SWD header on the board** — J_CART/J_LVC
  were removed in v2.2, and `J_SWD` was dropped in v2.3 (its pads at header
  pins 41-43 collide with the Plus-W pad grid; a Pico 2's own SWD
  castellations cannot be exposed on this footprint). Debug via TP1–TP8 and
  the USB console. If you ever need a specific U13-buffered signal on a
  scope, add a TP pad on the corresponding U13 output pin in
  `tools/gen_schematic.py`.
- **Pico 2 (module) only exposes 26 GPIO** on its headers (GP23–GP25 and GP29
  are internal). All 26 are consumed in the current design; there are no spare
  Pico GPIOs. Freeing one requires dropping a bus feature or adding an IO
  expander — see `docs/firmware-architecture.md` §9.1 for the v2 paths.
- **U15 is SN74LVC00A (SOIC-14)**, not SN74LVC1G11 (SC-70-6). v2.3 replaced
  the 3-input AND with a NAND-NAND decode on a quad-NAND part; gates 3/4 are
  grounded and unused. See the Hard rules section above for the wiring.
- **DNP by default (v2.3.1): R2, R10, R15, R17, Q3, C12, C15, J1.** Everything
  else is populated, including Q4/R16/R18 — the JP5-reachable `/CART` drive
  stage — which is populated on every build, not just Plus-W.
- **No mounting hole on the board.** MTG1 was removed in v2.3 (Task 4): the
  module's flat, horizontal placement leaves nowhere for it to clear. A
  future shell-fit board will need holes at shell-dictated positions instead.
- **Board outline is 98.0 x 77.16 mm overall** (67.0 mm body + 10.16 mm
  finger tongue; was 98 x 55 mm through v2.3). Grown 12 mm away from the
  fingers in v2.3.1 after a bench CoCo 3 measurement showed the shorter
  board put the module's USB-C port and the reserved HDMI corner on or past
  the case surface. See `docs/hardware-design.md` §6 and §9.

## Typical workflow in a new session

1. Skim the three docs under `docs/`.
2. If editing the schematic: modify `tools/gen_schematic.py`, rerun,
   open Eeschema, run ERC, fix, commit.
3. If editing the PCB layout: either drag in KiCad UI or edit `PLACEMENT` in
   `tools/place_pcb.py` and rerun. KiCad GUI is authoritative once routing
   has started.
4. Don't commit unless the user asked. If asked, check `git diff` for
   accidental v1 backup churn and add only the files that matter.

## Firmware (added 2026-09-07, spec: docs/superpowers/specs/2026-09-07-firmware-design.md)

- `firmware/` is the RP2350 firmware. Host build first: `cmake -B build-host
  -G Ninja -DPICOCO_HOST=ON firmware && ninja -C build-host && ctest
  --test-dir build-host --output-on-failure` (9 suites, ASan/UBSan). Pico
  target build is Plan B (not yet written).
- Board select: `-DPICOCO_BOARD=plusw` builds for the Waveshare
  RP2350B-Plus-W instead of the default Pico 2 (see `firmware/boards/` and
  `firmware/README.md`).
- **core1 must stay flash-free.** It runs only the bus loop from SRAM
  (`BUS_HOT`), never calls libc, logging or flash-resident code, and the
  build sets `PICO_FLASH_ASSUME_CORE1_SAFE` (not `PICOCO_FLASH_ASSUME_CORE1_SAFE`
  — that name never existed in the build). Anything core1 executes
  (`bus_on_*`, the Becker read hooks, `becker_refresh`) keeps that rule.
- **Single-writer Becker table:** only core1's read hooks on $FF41 and $FF42
  write `bus_table[0x3F41]`/`[0x3F42]`; core0 only pushes bytes. Do not add
  a core0 path that writes those entries.
- **The USB console (CDC1) is the only supported bring-up interface.**
  Milestones in `docs/breadboard-plan.md` §6 map to console commands (spec
  §8); `picoco.cfg` is a list of those commands replayed at boot.
- `docs/firmware-architecture.md` was rewritten to match Plan A; the
  PIO/DMA engine in its §3.3/3.4 is the v2 path, not what is built.
