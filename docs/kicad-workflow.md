# KiCad Workflow — PiCoCo v2.3

What's in the repo right now, what you do with it in KiCad, and how
to verify the design is correct at each step.

Current schematic/PCB revision: **v2.3** — carrier for either a
Raspberry Pi Pico 2 or a Waveshare RP2350B-Plus-W (`PiCoCo:Pico-Carrier`
footprint/symbol, generated), U10–U13 all `SN74LVC245A` at 3.3 V, U15
replaced by a `74LVC00` (SOIC-14) wired NAND-NAND, JP2/JP3 solder
jumpers, a populated-by-default sound stage to cart pin 35, no `J_SWD`
header and no mounting hole, fully routed with GND pours on both
layers, and an order-ready JLCPCB fab package under `fab/main/`.

## 2. What to do in KiCad (step by step)

### 2.1 Open the project

1. Launch KiCad.
2. `File → Open Project…` → select `PiCoCo/PiCoCo.kicad_pro`.
3. Symbol and footprint libraries should resolve automatically thanks
   to the fixed `fp-lib-table` / `sym-lib-table` (they now use
   `${KIPRJMOD}`).

### 2.2 Review the schematic

1. Open Eeschema (`File → Open Schematic` or the schematic icon).
2. You should see all the v2.3 components placed in a grid. **It
   won't be pretty** — the generator places components on a grid
   with pins connected via global labels touching pin endpoints.
   Global labels are the wiring.
3. Run ERC: `Inspect → Electrical Rules Checker`. Expect **1 error**
   and 0 warnings. The error is the cosmetic `pin_to_pin` between
   P1 Pin 33 GND@1 and P1 Pin 34 GND@2 (both declared `power_output`
   in the `PiCoCo:COCO-CART` symbol — a library-level quirk). Ignore.
4. Optional — reshape the schematic for readability:
   - Rotate/move components so wires are visually obvious.
   - Convert clusters of global labels into net labels + short wires
     for nearby pins.
   - None of this affects the netlist; it's only for human reading.

### 2.3 Sync the PCB

1. Close the schematic editor first (KiCad holds file locks).
2. From the PCB editor: `Tools → Update PCB from Schematic…`
3. **Tick "Delete footprints with no corresponding symbol"** so old
   orphans get cleaned up automatically.
4. Regenerating from a pre-v2.3 board, expect this diff (already
   applied to the committed board — this is what Task 4 saw going
   from v2.2 to v2.3):
   - **U1** footprint changes from `RPi_Pico_SMD_TH` to `Pico-Carrier`
     (adds the 15-pad Plus-W grid, drops the SWD pads and pins 41-43).
   - **U10–U13** stay `SOIC-20W` but the symbol's value changes to
     `SN74LVC245A` on all four (U10 included — no more `SN74LVC8T245`).
   - **U15** footprint changes from `SC-70-6` to `SOIC-14` (`74LVC00`
     replaces `74LVC1G11`). KiCad removes the old footprint and adds
     the new one at origin.
   - **Removed**: `J_SWD`, R6, R13, R14, JP1, C5, C11 and their nets.
   - **Added**: JP2, JP3 (SMD solder jumpers), Q3/Q4 (SOT-23, DNP),
     R15–R22, C12–C15, TP7, FID1/FID2.
   - **Net renames**: `RESET_DBG` → `RESET_BUF`; new nets `SEL_N`,
     `OE_BUS_RAW` (U15's internal NAND-NAND node), `OE_FW`, `NMI_DRV`,
     `CART_DRV`, `PICO_P34`, `AUDIO_PWM`, `AUDIO_F1`, `AUDIO_F2`,
     `SND_CART`. Any hand-routed traces on surviving nets are
     preserved under their new names as long as the endpoints match.
5. Confirm. New footprints land at origin; the board as committed has
   already been placed and routed (see §"Routing") — don't run
   `place_pcb.py` again unless you intend a full reroute.

### 2.4 Place components

`tools/place_pcb.py`'s `PLACEMENT` dict is the source of truth for
coarse placement (row nearest the fingers: U10–U13 in signal order;
U14/D2/C1–C3/C12 near the +5V finger; Q2/R1 near /HALT; Q3/Q4 near
/NMI and /CART; JP2 next to U10 pin 19; the audio stage in a line
ending at the SND finger; JP3 next to the module's pin 34). Running it
against the routed board destroys routing — see §"Routing" below for
when you actually want to touch placement again.

### 2.5 Routing

See the dedicated **Routing** section below — the board was not routed
by hand track-by-track in the GUI; it went through an autoroute +
grid-route + pour pipeline, then a small amount of GUI hand-finishing.

## Routing

The routed board (`PiCoCo/PiCoCo.kicad_pcb`) came from this pipeline,
all four tools run under **KiCad's bundled Python**
(`/Applications/KiCad/KiCad.app/Contents/Frameworks/Python.framework/Versions/Current/bin/python3`)
because they drive the `pcbnew` API:

1. **`tools/autoroute.py BOARD [--passes N] [--out OUT] [--jar JAR]`**
   — exports a Specctra DSN, calls Freerouting, imports the resulting
   SES, and cleans up dangling vias / zero-length stub segments.
   Freerouting (`freerouting-2.4.1.jar`) is **untracked** and sits at
   the repo root — too large for git, and never add it. It needs
   **Java ≥ 25**: use `/opt/homebrew/opt/openjdk/bin/java`, not
   whatever's on `$PATH` (SDKMAN's JDK 21 fails with
   `UnsupportedClassVersionError`). It writes under `~/Library/Application
   Support/freerouting` and `~/Library/Logs/freerouting` and must run
   with the **Bash sandbox disabled** — run `autoroute.py` itself
   sandbox-disabled too, since it launches Freerouting as a
   subprocess (sandboxed, Freerouting hangs in a log4j retry loop).
2. **`tools/grid_route.py BOARD [--out OUT] --pair NET x1 y1 x2 y2 [--pair ...]`**
   — an A* router over `pcbnew`'s collision shapes, for the handful of
   nets Freerouting leaves unrouted (on this board: `SLENB_BUF`,
   `E_BUF`, `AUDIO_PWM`, `PICO_RUN`, `PICO_P34`, plus `A6_BUF` and
   `A11_BUF` after ripping up some GND stub tracks to free a corridor —
   GND is carried by the pours, so short GND stubs can be sacrificed
   and restored by re-pouring + stitching).
3. **`tools/pour.py BOARD [--out OUT]`** — adds/refreshes the GND pour
   on both F.Cu and B.Cu, board outline inset 0.3 mm, cut 1 mm above
   the edge fingers so the pour never reaches the gold-fingered area,
   and fills.
4. **`tools/gnd_fix.py BOARD [--out OUT] [--drc DRC_JSON]`** — links
   any stray GND clusters (pads, vias, pour islands) that the pour
   left electrically isolated. Pass a `kicad-cli pcb drc` JSON with
   `--drc` and it also fixes starved-thermal pads it finds in the
   report.

**Rip-up-and-reroute a net**: delete that net's existing tracks/vias
via the pcbnew API (a short one-off script, or in the GUI), then
re-run `grid_route.py --pair NET ...` for it, then `pour.py` +
`gnd_fix.py` to restore ground continuity, then DRC.

None of these four tools are a "regenerator" like `gen_schematic.py` —
they're aids for getting from an unrouted board to a routed one. **The
routed board in `PiCoCo/PiCoCo.kicad_pcb` is hand-finished and
authoritative**; the KiCad GUI is the source of truth once you've
routed in it, same as the existing rule for any manual PCB edit.
Re-running `place_pcb.py` on it will destroy the routing.

Two board properties worth knowing before you touch routing:

- `place_pcb.py`'s `EXTRAS` list writes four track/via keepout zones
  around U1's NPTH holes (the USB-connector legs) — DRC's
  `hole_clearance` rule isn't expressible in a DSN export, so
  Freerouting doesn't know to avoid them without this.
- **U11 pad 10 (GND)** has zone connection **"none"** rather than a
  thermal-relief spoke — it's tied to the GND pour by track + via
  instead, because the automated pour left it a starved thermal.

**Design rules actually in effect** (`PiCoCo.kicad_pro`, one Default
netclass, no power netclass): 0.20 mm track / 0.15 mm clearance, vias
0.8 mm pad / 0.4 mm drill (a few 0.6/0.3 mm vias used for GND
stitching). Design-rule floors: min track 0.127 mm, min clearance
0.127 mm, copper-to-edge 0.2 mm, min hole clearance 0.25 mm. `+5V` and
`VSYS_PICO` run at the same 0.20 mm as signals — margin is fine for
the cartridge's 300 mA budget at 1 oz copper.

**Final DRC** (`kicad-cli pcb drc --severity-all --schematic-parity`,
sandbox disabled): **0 errors, 0 unconnected, 0 schematic-parity
issues, 77 silkscreen warnings**. The warnings are reference
designators sitting over pads/board edge — not fab-blocking (JLCPCB
clips silkscreen that overlaps copper or the edge automatically) —
and are left as-is rather than chased down further.

## 2.6 Paste and stencils

**No module pads carry F.Paste** — neither the 40 through-hole/
castellation pads nor the 15-pad Plus-W grid. The module is never
factory-placed (it's soldered by hand, flat, with nothing under it),
so paste there would leave solder bumps under a part that can't be
reflowed in place. This means the production `F.Paste` Gerber
(`fab/main/PiCoCo-F_Paste.gtp`) has paste flashes only on the parts
JLCPCB's assembly line actually places.

`fab/main/stencil-module/PiCoCo-stencil-module-F_Paste.gbr` is a
**separate** stencil Gerber, produced from a temporary in-memory copy
of the board with U1's pads (castellations + grid) given an F.Paste
layer — nothing in the checked-in board or footprint changes. Cut this
as its own stencil if you're hand-soldering the module with hot air or
a paste syringe (mainly relevant for a Plus-W's 15 hidden pads; a
header-mounted Pico 2 doesn't need it at all).

## 2.7 JLCPCB files

`tools/gen_fab.sh` (via `tools/jlc_post.py`) produces, under
`fab/main/`:

- **`PiCoCo-BOM-jlc.csv`** — Comment, Designator, Footprint, LCSC Part
  #, MPN; grouped by value; DNP parts excluded.
- **`PiCoCo-CPL-jlc.csv`** — Designator, Mid X, Mid Y, Layer, Rotation.
  Rotation comes from `kicad-cli pcb export pos` plus a per-footprint
  offset table in `tools/jlc_post.py` (keyed by package substring:
  `SOIC-20W`, `SOIC-14`, `SOT-23`, `SOT-223`, `D_SMA`, `0805`,
  `CP_Elec`), meant to be checked once against JLCPCB's placement
  preview and then fixed with the date it was verified. **As of this
  writing every offset is still 0 — the rotation table has not yet
  been checked against JLCPCB's preview.** Don't assume placements are
  correct without that check; fix the table and rerun `gen_fab.sh` if
  the preview shows a part rotated wrong, then re-upload.
- Fiducials (`FID1`, `FID2`) currently still appear in the CPL —
  `kicad-cli`'s `--smd-only` flag treats the fiducial footprint as SMD
  at the PCB level. JLC's assembly process typically ignores fiducial
  refs in a CPL; left as-is rather than filtering it out.

## 3. Regenerating the schematic

If you want to change pin assignments or add components, edit
`tools/gen_schematic.py` (declarative — modify the `pin_nets`
dictionaries and the `SYMBOLS`/placement calls) and re‑run:

```bash
python3 tools/gen_schematic.py
```

This also rewrites `libraries/PiCoCo.kicad_sym` (the `Pico-Carrier` and
`74LVC00` symbols) and `libraries/PiCoCo.pretty/Pico-Carrier.kicad_mod`
as a side effect — never hand-edit those two files directly. The
script's `check()` runs automatically after `build()` and fails the
regeneration on a typo'd single-pin net, a banned `_B`/`_DBG` net name,
U10's A/B side ordering, U15's decode wiring, JP3's wiring, or a
missing `LCSC` on a non-DNP, in-BOM part.

Then:
1. **Close Eeschema first** (file‑lock races otherwise).
2. `python3 tools/gen_schematic.py` — overwrites the .kicad_sch.
3. Reopen Eeschema, run ERC. Expect the one known error, 0 warnings.
4. PCB editor: `Tools → Update PCB from Schematic`, **with
   "Delete footprints with no corresponding symbol" ticked**. This
   removes orphans from net renames.
5. If you added footprints, `python3 tools/place_pcb.py` will place
   only unsynced refs (it reports refs it can't find). **Do not** run
   it if you only touched electrical wiring on already-placed parts —
   it will re-place everything and discard routing.
6. Refill zones (`B` in pcbnew), rerun the Routing pipeline for any
   newly unrouted nets, run DRC, address any issues.

`tools/gen_breakout.py` (also under KiCad's bundled Python — it drives
the pcbnew API) imports from `gen_schematic.py` but does not use the
`Pico-Carrier` symbol/footprint; it must still run and reproduce an
identical breakout after a generator change (diff the generated
files against the committed `breakout/`).

## 3.1 Generating fab outputs

```bash
bash tools/gen_fab.sh
```

Needs the sandbox disabled (`mktemp -t` for the stencil temp copy is
blocked under the sandboxed shell). Produces Gerbers, drill, JLC
BOM/CPL, the module stencil, and a zip under `fab/main/`. The shipped
`fab/main/READ-BEFORE-ORDERING.txt` is the checklist for JLCPCB: ENIG
surface finish, hard gold fingers, 30° bevel, 1.6 mm board, the DNP
list, and a budget bare-board variant. **Do not skip it** — JLCPCB's
defaults will not gold-plate the cartridge fingers.

`tools/gen_fab.sh [pcb] [outdir]` also still works for the two
breakout boards (pass their path explicitly).

## 4. Common gotchas

- **Symbol library errors on open.** KiCad may complain that
  `PiCoCo:Pico-Carrier` or `PiCoCo:COCO-CART` is not in the global lib.
  That's fine — the symbols are embedded in the schematic's
  `lib_symbols` block, and the project-scoped `sym-lib-table`
  points at `${KIPRJMOD}/../libraries/`. If KiCad still complains,
  check `Preferences → Manage Symbol Libraries → Project Specific
  Libraries` shows a `PiCoCo` entry.
- **Footprint not found on "Update PCB from Schematic".** All
  footprints use standard KiCad libraries except the edge
  connector (`PiCoCo:COCO-CART-2.1X1.75`) and the module
  (`PiCoCo:Pico-Carrier`). Both come from the project's local
  `fp-lib-table`. If KiCad complains about any standard one
  (e.g. `Package_SO:SOIC-20W_7.5x12.8mm_P1.27mm`), check
  `Preferences → Manage Footprint Libraries → Global Libraries`
  and make sure the standard KiCad libraries are enabled.
- **`kicad-cli pcb drc` crashes with a Swift runtime error only inside
  the Claude Code sandbox** — run it with the sandbox disabled, and
  make sure `PiCoCo.kicad_pro` sits beside whatever `.kicad_pcb` you
  point it at, or it silently falls back to KiCad's stock design
  rules instead of this project's.
- **ERC warnings about `tri_state` pins.** Fixed in v2.3 by retyping
  the embedded `74LS245` copy's data pins to `passive` in the
  generator — if you see these warnings return after a generator
  change, check that retyping step wasn't reverted.
