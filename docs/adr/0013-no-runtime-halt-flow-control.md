# /HALT is not DriveWire flow control; a runtime hold is bounded to 500 µs

The 2026-09-07 firmware design left room for a `halt_assert()` around flash writes of a few milliseconds, and ADR 0006 keeps Q2 partly because the pin "doubles as DriveWire flow control". Neither was built: reading the 2026-10-28 source, the only writers of `HALT_GATE` are the Halt hold and its release in `main.c` and the manual console `halt on|off`; the DriveWire path paces the CoCo through the Becker status register at $FF41 and the CoCo's own polling, never /HALT, so the automatic runtime hold today is zero (by inspection, not a scope). The decision is to keep it that way. NitrOS-9 keeps time from the 60 Hz VSYNC interrupt (the GIME on a CoCo 3, the PIA on a CoCo 1/2), one tick every 16.7 ms, and the interrupt is a latched flag: a hold that covers two VSYNC edges, so longer than a tick, loses the clock one tick, and any hold delays every interrupt behind it. The Halt hold (about 1.2 s, ADR 0006; about 16 s with `becker net`, `docs/firmware-architecture.md` §7.3) happens before any OS is running and stays, and the console's `halt on` is a bring-up tool a person releases by hand, outside the bound. If a future device needs an automatic runtime hold (a flash write while the CoCo waits for a reply, a Disk-Pak-style per-byte halt), it is bounded to 500 µs, thirty times under a tick, and measured on a scope at the HALT_GATE pin before it ships; work that needs longer is split or moved off the hot path instead. Bench check: `firmware/TEST_PLAN.md` H.3 step 6.
